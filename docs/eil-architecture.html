Design thesis

Two kinds of AI systems, opposite strategies. Amp and Copilot are closed — collect from their admin APIs, never intercept. MaaS is controlled — every call routes through one gateway, the choke point where cost, tracing, routing, and budgets live. Around that split: a telemetry plane that unifies three differently-shaped cost sources, a knowledge plane that answers deterministically for zero tokens, and an orchestration plane where scripts own control flow and call models as functions.

C1 MaaS = non-frontier only (Nemotron-class) C2 no local models, no local Docker — hosted kube only C3 ELK = hosted logging cluster, logs-only, not extendable C4 Atlassian Data Center estate (Bitbucket · Bamboo · Jira · Confluence)

03Heavy critique — the whole solution

The knowledge plane's own eight risks live in the companion brief. These are the solution-level ones — several would sink the project regardless of how well any single plane is built.

MCP identity propagation is the weakest link in the ACL story

High

The retrieval service filters by caller identity — but how does it know the caller? If teams configure the MCP server in Amp/Copilot with one shared service account, every ACL in the knowledge plane is theater: everyone searches as the service account. This is the single most likely way the platform causes a data incident, and it fails silently.

ResponsePer-user credentials, non-negotiable: OAuth device flow or short-lived per-user tokens issued by the retrieval service, distributed via managed MCP config — never a shared key in a team wiki. Audit-log every call with resolved identity. CI red-team test: a planted restricted doc must not surface for a wrongly-scoped token.

You are building the org's most attractive honeypot

High

Code, tickets, wiki, meeting transcripts, and per-user activity — aggregated, indexed, and reachable through one service. The EIL concentrates more sensitive data than any system it reads from. Its blast radius on compromise exceeds any single source system's, and security review will (correctly) treat it that way.

ResponseThreat-model before wide rollout, not after. Encryption at rest, secrets via vault, network policies isolating the namespace, transcripts behind the strictest tier with retention clocks, and the security team engaged at design time — being invited early is cheaper than being discovered late.

The gateway is a single point of failure on every workflow's critical path

High

LiteLLM is a fast-moving Python project, not battle-worn infrastructure. When it's down, every judgment step in every workflow stops — and because it's also the budget enforcer, teams will lobby to "temporarily" bypass it, which permanently destroys cost attribution.

ResponseHA replicas behind a service, stateless config in git, pinned versions with staged upgrades, health-based failover. Politically: bypass is impossible by policy and by network — MaaS credentials live only in the gateway's namespace. If ops pain persists two quarters, the runner-up (Kong AI Gateway) is the planned exit.

Nemotron ceiling: judgment quality will disappoint before cost does

Med

Mid-tier models handle narrow structured judgment well, but users compare every output to what Amp gives them interactively — frontier quality. Mediocre PR-review comments erode trust in the whole platform, not just that workflow. Meanwhile the F5b escape hatch bills in Amp credits, which can quietly exceed what frontier API calls would have cost.

ResponseEval gates decide each workflow's tier with data, not optimism; workflows that fail eval at Nemotron tier ship via F5b or don't ship. Track F5b cost-per-run from day one — it's in the fact table already. Re-run the tier decision whenever the MaaS catalog changes.

Vendor APIs own your telemetry roadmap

Med

F1 depends on Copilot and Amp admin APIs you don't control: granularity is coarse (per-user tokens for Copilot don't exist), schemas change without your consent, and lag is ~24h. Collector rot is the telemetry plane's version of connector rot.

ResponseContract tests against both APIs; staleness alarms per collector; dashboards annotate granularity honestly (Copilot = seats + premium requests, never tokens) so nobody builds decisions on false precision. Named owner, same as knowledge-plane connectors.

Identity drift corrupts attribution quietly

Med

Joiners, leavers, GitHub handle renames, contractors with two accounts — the identity map decays continuously, and misattributed spend discredits the dashboards the moment a team lead spots their own name wrong.

ResponseNightly reconcile against AD/LDAP as source of truth; unmapped-identity alarm (any usage row that can't resolve pages the owner); history kept so past spend re-attributes correctly after a fix.

Adoption risk: indexes nobody queries are pure cost

Med

The plane only pays off if Amp sessions and workflows actually call the MCP tools. If setup friction is high or results disappoint early, agents keep "exploring" expensively and the EIL becomes shelfware with an on-call rotation.

ResponseMeasure MCP tool-call volume per team from week one — it's the platform's north-star metric, on the same Grafana board as cost. Ship team-default Amp/MCP configs so the tools are present without setup. The expand("PAY-981") demo is the adoption wedge; lead with it.

Platform weight: ~8 stateful-ish services need a named owner

Med

Gateway, retrieval service, OpenSearch, Zoekt, Postgres, Langfuse, collectors, connectors — plus dashboards. Built as a side project, this rots in six months; the failure mode isn't an outage, it's slow decay into distrust.

ResponseTreat EIL as a product with an owning team and an on-call story before phase 3. Trim weight where possible: start OTel-only instead of Langfuse, defer Temporal, defer embeddings — every deferred service is real risk reduction. The build order below is sequenced so each phase is independently valuable if investment stops there.

04Build order

Weeks 1–3

Gateway + cost floor

LiteLLM HA on kube, virtual keys. Amp + Copilot collectors, identity map, fact table, first Grafana board.

exit: total AI spend answerable in one query · F1 + F2 live
Weeks 4–6

Observability

OTel GenAI spans → Grafana; budgets + anomaly alerts; implicit quality signals. Langfuse only if OTel-only proves insufficient.

exit: latency, errors, cost-per-task per model · F6 skeleton
Weeks 7–10

Knowledge plane core

Catalog + link graph + Jira/Confluence connectors, then Zoekt + SCIP. ACL gate + per-user MCP auth + red-team eval before rollout. BM25-only; embeddings deferred.

exit: F3 + F4 live · expand("PAY-981") demo · MCP call volume on dashboards
Weeks 11+

Workflows, evals, and semantics

PR review + incident triage as first pipelines, eval-gated tiering (Nemotron vs F5b). Golden-set retrieval CI. Add kNN arm + embeddings only where evals show the gap. Transcripts + Obsidian write-back last.

exit: two workflows in production with cost + quality tracked · F5 live
