Observability & monitoring

Cost, model performance, platform health, and adoption — measured where the facts already live, with SQL views as the metrics layer and Grafana on top.

2026-07-27 · Draft 1 · companions: full solution rev 2 · knowledge plane draft 4.2

Design thesis

The knowledge plane already emits its own telemetry as a side effect of working: every MCP call lands in audit_log, every model call in llm_calls, every sync advances sync_cursors, every eval produces recall numbers. Observability v0 is therefore not a new system — it is SQL views over facts that already exist, plus collectors for the two vendors, plus Grafana reading Postgres directly. Metric definitions are versioned, deterministic SQL in git — testable like everything else. No new datastore, no agent required to answer “what happened.”

Two derived metrics deserve their names: zero-result rate (searches returning nothing — each one is a corpus gap, a router miss, or a semantic-arm argument, and the instrumented failure data that schedules Zoekt/embeddings), and the two-phase ratio (get_doc calls per search — near 1.0 means agents fetch selectively as designed; well above means snippets are too weak, near 0 means results aren’t worth opening).

03Honest critique

  • Grafana-on-Postgres has a scaling cliff — dashboard queries hit the same instance agents query. Fine for years at this volume; the metrics schema keeps the eventual split (read replica, or Prometheus at kube) a connection-string change. Watch retrieval p95 for dashboard-induced noise.
  • “Tokens saved” is an estimate, not a measurement. It compares tool-call context sizes against an assumed exploration baseline. Label it estimated on the dashboard; the defensible numbers are call volume, zero-result rate, and vendor-billed spend.
  • The identity map remains the weakest data. Collectors land vendor-keyed rows; joins are only as good as identity_map. The unmapped-rows alarm is the tripwire — treat any unmapped usage as a data bug, not noise.
  • Local mode observes one user. Adoption boards are trivial until the kube promotion; their value starts at P2. Build them anyway — the views and dashboards are identical, only the row count changes.
  • eval_runs needs eval entries to mean anything. Two fixture queries make a smoke test, not a baseline. The golden log growing from real usage is still the gating dependency for the Model Performance board’s recall panel.

04Implementation phases

O-0
~2 days

Facts and views

Migration: metrics schema, usage_facts, eval_runs, identity_map, and the first six vw_* views. eil eval writes eval_runs (with git sha). View tests in the red-team pattern: seeded facts in, expected aggregates out.

exit: every dashboard panel answerable by SELECT from a view
O-1
~2 days

Grafana, provisioned

brew-service Grafana + Postgres datasource + the four dashboards as provisioned JSON in observability/. Alert rules for cursor age, zero-result spike, recall drop.

exit: dashboards live locally from repo JSON alone — a second machine reproduces them with two commands
O-2
~3 days

Vendor collectors

eil collect amp (admin API → per-user credits) and eil collect copilot (metrics + billing → seats, premium requests, acceptance) with contract tests against recorded fixtures; identity_map seeded and alarmed. Needs org API tokens — the first org-access dependency in this plane.

exit: one Grafana panel shows true org AI spend across all three sources
O-3
kube

Promotion + gateway telemetry

Collectors become CronJobs; Grafana a Deployment; LiteLLM ships OTel/webhook events into usage_facts for exact per-request MaaS cost; alert webhook → ticket-filing workflow. Gated behind the P1/P2 promotion gates like everything else.

exit: rev 2 brief’s F1/F2/F6 flows fully realized
