Retrieve §6

Router

entity · docs · symbol · path · exact. Deterministic classifier, no LLM. Unchanged.

↓   fan out to arms   ↓
Prose arm — BM25

Prune the query by document frequency before the scan, then score with real BM25 (k1=1.2, b=0.75). setweight('A') on the breadcrumb.

today: ts_rank has no IDF — "work" counts as much as "backoff"
Code arm — Zoekt scorer

Subtoken tokenizer (one function, index and query). Score composes by MAX, never SUM. No IDF here — Zoekt's own evals reject it for keyword queries.

today: exact equality only, and no ranking at all
Vector arm — the funnel

IVF cluster probe → Hamming on sig → exact float4[] rescore of survivors. Oversample fixed at 8×; nprobe is calibrated, not guessed (§12.1).

1.30 µs/chunk vs 298.5 — 230× storage 30 MB → 1035 kB

Oversample is not the knob — nprobe is. 8× and 16× are identical at every setting, which means that once survivors are rescored exactly, binary quantization costs nothing: all loss is clusters not probed. This corpus (21 chunks/cluster) is too small to set nprobe from, so the spec ships a calibration procedure with a ≥0.98 gate and a fallback to full scan — not a constant.

Sequencing — evaluation gates the rest

  1. Instrumentation. audit_log columns, try/finally so failures are logged, trace_id, missing indexes. Nothing below is measurable without it — and it produces the real queries step 2 needs.
  2. Ingestion correctness. Metadata hash · code timestamps · cursor safety · retry · per-chunk embed reuse · owner threaded into acl_groups.
  3. Evaluation harness. 150–200 queries, ~50 replayed from step 1's logs. Recall@50 + Recall@10 + nDCG@10, pooled graded judging, paired permutation test. Everything below must beat p < 0.05.
  4. Cheap retrieval wins. Embedder singleton (60–75×) · chunk/window match · MaxP · filters · ±1 neighbour chunk. Anything that fails to help is reverted, not kept.
  5. Storage for scale. sig / cluster_id / ivf_centroids · lexeme_stats · tsv_code — plus the IVF calibration run.
  6. Retrieval substance. Vector funnel · BM25 · code executors · fusion recalibration.
  7. Ingestion breadth. Git history · cross-source links · Jira and Confluence field coverage.
  8. Eval-gated options. Reranker · second embedder · learned sparse arm — each requires demonstrated headroom.

Step 1 before step 3 is the non-obvious dependency, and it explains a symptom already visible: docs/golden-queries.md has held two entries for its lifetime while asking for entries "from actual usage." Nothing in the system currently produces usable usage records. Persisting the two fields searchDocs already computes and discards turns the audit log into the eval corpus.

Deliberately not built

HyDE · LLM query expansion inside EIL · Self-RAG / CRAG / Adaptive-RAG loops · Microsoft GraphRAG · memory layers · RAPTOR · semantic / breakpoint chunking · function-level-only code chunking · SCIP / LSIF / stack-graphs · ColBERT as first stage · IVFFlat · any API reranker · pg_search / pg_textsearch / VectorChord as hard dependencies.

The pattern: each spends LLM tokens on something the calling agent already does better with full task context, or that a deterministic method captures at ~0.1% of the cost. GraphRAG is the sharpest case — it pays $20–50/M tokens to hallucinate approximations of the exact typed edges EIL already has in links and does not yet use in the docs route.
