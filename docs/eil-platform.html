EIL · the platform view

You already have a pipe to each system. This is the index across them. Five steps take a question from four sources to one ranked, permission-filtered answer — with no model anywhere in the retrieval path. That last part is why the next service costs a prompt instead of a project.

How it worksa question, end to end

The full map has seven planes and every wire drawn. This is the same thing with the detail taken out.

01

Connect

Confluence spaces, Jira projects, Git repos, notes and runbooks.

Scoped, and on your own credentials — you can only index what you could already read.

02

Index

One Postgres. Text and meaning in the same table, no extension to install.

Re-running is a diff: unchanged pages are skipped on a hash, a repo on its commit SHA.

03

Retrieve

Four keyword arms and one meaning arm, merged by rank position.

No model runs here. Same question, same answer, every time.

04

Serve

Two calls. A search returns ids and one-line previews; the agent opens only what it wants.

Six tools, one of which writes.

05

Watch

Every search and every fetch is a row: who asked, what matched, how long it took.

What people ask and can't find is the input to what gets indexed next.

Governance

Not a step — the floor all five stand on. Visibility is stamped on the document, so an unstamped one is readable by its owner and nobody else. A restricted page isn't refused or redacted: it is absent, with nothing in the response to notice. The failure direction is fixed — a bug can only ever show you less.

Why another service is cheapmeasured, not projected

Two things make the marginal service affordable. Retrieval spends no model tokens at all — it is a database query. And when a model is finally involved, it reads what it chose to open rather than everything that matched.

Drawn to scale from this repo's own corpus, at the narrowest gap of the four questions the demo actually asks. Across those four the saving runs between 6.5× and 10× — it depends on the question, so the bar below is drawn at the worst of the four. Run eil context-cost "<your question>" for a number that is yours rather than mine.

Quote the per-match pair, never a single headline ratio. A whole-query ratio also moves with how many documents matched — on one query here it went from 1.5× at four matches to 4.9× at nineteen — because the one document the agent opens is a fixed cost that amortises. And the whole argument holds only while the agent stays selective: open every match and the saving is gone. The tool measures that case too rather than hiding it.

What each one actually needsso the estimate isn't a guess

Already thereWhat a new service still has to bring
Connectors Nothing, if it reads sources already indexed. A new kind of source needs an adapter — a day or two, and it normalises into the same document shape as everything else.
Retrieval Nothing. It calls search_docs like any other caller and gets the same ranking, the same permissions and the same audit row.
Permissions Nothing, and it cannot opt out. Every read goes through the same gate; there is no path around it to forget to use.
The service itself A prompt, a pattern of tool calls, and a surface people use. That is the real work, and it is the part that differs between a wiki search box and an incident copilot.

Read this before quoting any of it

"Built" means built and demonstrable in this repo. "Proposed" means designed on paper and nothing more — no code, no estimate that has survived contact with a real corpus. The distinction is on every card deliberately.

Two limits that bound all of it. No connector stamps groups yet, so a live Confluence sync gives owner-level visibility only — the enforcement is real, the group feed is not. And logs are proxied, not indexed: they are queried live, recency-sorted and capped, which is a deliberate choice about a high-volume, sensitive firehose rather than a missing feature.
